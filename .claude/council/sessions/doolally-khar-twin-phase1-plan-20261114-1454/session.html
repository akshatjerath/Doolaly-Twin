Architect Position: Phase 1 module structure, sim/render contract, layout and params data

Core recommendation: Build around one pure, three-free simulation core that outputs an append-only event log. KPIs are pure reducers over that log. 3D agents are a playback cursor over the same log. The Web Worker is a thin message adapter around the core. Layout geometry (layout.json) and numbers (params.json) are kept as two separate files, both validated at boot and in CI.

Key argument: The brief's hard rule 2 ("one source of truth") is a data-flow rule, so the structure should make breaking it hard. src/sim holds rng, engine, kpi and stats as pure TypeScript with no DOM and no three. The same code runs in Vitest (Node) and in the worker. The engine emits typed events (ARRIVE, QUEUE_JOIN, BALK, RENEGE, SEAT, DEPART, LOUNGE_ORDER, TAKEAWAY_SALE, CLOSE). kpi.ts turns any log into a KPI vector. That covers walk-away %, all-arrival wait (reneges and still-queued parties at CLOSE count as censored), median, p90, utilisation, revenues and lost parties. The HUD never computes; it only formats kpi.ts output. agents/playback.ts keeps a cursor into the hero log and derives "who is where" at sim time t, so the timeline scrubber is just a cursor seek. Replications use common random numbers: each replication seed spawns independent RNG streams per process (arrivals, party, patience, dwell, conversion), and every scenario uses the same seed list. Paired deltas then measure the intervention, not RNG drift. The hero run is replication 0 of that same seed list. The animated night is therefore one of the 200 runs behind the CI, never a separate "demo" run. Batch replications return only KPI vectors (no logs), so memory stays flat at N >= 200 x 4 scenarios.

Risks if ignored:

  • Structural: If agents get their own movement logic (a "visual sim"), the counts on screen will drift from the KPIs. That repeats the Gemini failure (hardcoded HUD numbers, survivorship-biased wait).
  • Performance: Sending full logs for 800 runs, or running the sim on the main thread, stalls rendering. Streaming per tick adds message chatter. Sending the whole hero log once (thousands of small events) is cheap.
  • Integration: Seating capacity is unknown (user recall "0-75", per-zone split unknown). If it gets baked into layout geometry, every answered open question becomes a code change. Capacity must stay in params.json (tagged, slider). Layout should only give rectangles that the scene fills procedurally.

Dependencies on other domains:

  • Alchemist / Skeptic: an exact definition of censored wait and the CI method (t-interval on per-replication means; paired-difference CI). I fix the data shape, they fix the estimator.
  • Craftsman: test layout and the "sim imports no three/DOM" guard test; a golden-log determinism test (same seed gives a byte-identical log).
  • Tuner / Artisan: an agent rendering budget (instanced vs skinned) that consumes playback.ts state, plus a hard cap on concurrently animated agents.
  • Advocate: the HUD's rendering of "Insufficient evidence" and the licence-gate copy. The gate itself is enforced in the worker (see appendix).
  • Dependencies: three, postprocessing, vite, typescript, vitest. No zod, no state library, no React: the validator is about 40 lines and unit-tested.

Appendix B: Worker message contract

// src/sim/protocol.ts
type ScenarioId = 'baseline' | 'A' | 'B' | 'C';
type ParamOverrides = Partial<Record<ParamKey, number>>;   // slider values only

type ToWorker =
  | { type: 'hero';  runId: number; scenario: ScenarioId; overrides: ParamOverrides; seed: number; licenceAssumed: boolean }
  | { type: 'batch'; runId: number; scenarios: ScenarioId[]; overrides: ParamOverrides; baseSeed: number; n: number; licenceAssumed: boolean }
  | { type: 'cancel'; runId: number };

type FromWorker =
  | { type: 'heroLog';  runId: number; scenario: ScenarioId; seed: number; events: SimEvent[]; kpis: Kpis }
  | { type: 'progress'; runId: number; done: number; total: number }
  | { type: 'batchResult'; runId: number; n: number; seeds: [number, number];
      byScenario: Record<ScenarioId, KpiSummary>;           // mean, ci95, median-of-reps
      pairedVsBaseline: Partial<Record<ScenarioId, KpiSummary>> }
  | { type: 'error'; runId: number; code: 'INVALID_PARAMS' | 'LICENCE_GATED' | 'CANCELLED'; message: string; details?: Record<string, string> };

type SimEvent = { t: number; partyId: number } & (
  | { kind: 'ARRIVE'; size: number }
  | { kind: 'QUEUE_JOIN'; quotedWait?: number }            // A: point estimate shown
  | { kind: 'BALK' } | { kind: 'RENEGE' }
  | { kind: 'SEAT'; zoneId: string; tableId: string }
  | { kind: 'DEPART' }
  | { kind: 'LOUNGE_ORDER'; amount: number }               // B only
  | { kind: 'TAKEAWAY_SALE'; amount: number }              // C only
  | { kind: 'CLOSE' } );                                   // censoring marker

type KpiSummary = Record<KpiKey, { mean: number; lo: number; hi: number } | null>; // null -> "Insufficient evidence"

Rules: the worker re-validates overrides against params.json bounds (trust boundary: sliders and any URL share state). It rejects B/C with LICENCE_GATED unless licenceAssumed, so the gate holds even if the UI is bypassed. The client drops any message whose runId is stale (slider dragged mid-batch). Seeds are baseSeed + i, i = 0..n-1, identical across scenarios. Hero uses seed = baseSeed.

Alchemist Position: Parameter registry and DES model design

Core recommendation: Treat params.json as a validated data contract and the event log as the only fact table. Every KPI is a pure function of (params hash, seed, scenario, event log). Almost every behavioural and capacity input is ASSUMED with a slider. Revenue outputs return null / "Insufficient evidence" whenever an input they need has no source and the user has not entered a value.

Key argument: Grain first. (1) event: one row = one state change for one party in one replication (rep, scenario, seed, t_min, party_id, type ∈ {ARRIVE, BALK, QUEUE, SEAT, RENEGE, DEPART, LOUNGE_JOIN, TAKEAWAY_ORDER, TAKEAWAY_DONE, HORIZON_CENSOR}, table_id, pax). (2) party: one row = one party per rep per scenario. It holds arrival, outcome, wait_min, censored(0/1), and every random draw is made at arrival. (3) rep_kpi: one row = one rep × one scenario. (4) run_manifest: params hash, engine version, base seed, N. The UI reads rep_kpi aggregates. A full event log is kept only for the replication being animated. The other replications keep only party and KPI rows (order of 10^5 rows; size depends on the ASSUMED arrival rate).

Registry contract. The brief's fields are {value, unit, tag, source, confidence, note}. I propose two optional fields: range: [lo, hi] (required when tag = ASSUMED, because this is what the slider uses) and gate: "B" | "C" for licence-unconfirmed scenarios. A Vitest check rejects the file if any of these hold: a tag is outside the enum; VERIFIED/OBSERVED has no register row id (e.g. D5); ASSUMED has no range; a price field has a value with no source. A number with no evidence is stored as value: null, tag: "ASSUMED", note: "Insufficient evidence" until the user sets it. Gemini's defaults (8-seat benches, 20-34 / 46-68 min patience, Rs 680/head, 72% conversion, 24% mug club, +38% match nights, 18-guest permit lounge) are excluded.

Behavioural papers A1-A3 (direction only). A2: relative-progress information reduces reneging. A3: point estimates reduce balking compared with intervals, and coarse intervals raise reneging. A1: longer waits go with reneging and shorter dining. We encode these only as sign constraints on scenario-A multipliers. The balk multiplier must sit in a range with upper bound 1.0. The patience multiplier must sit in a range with lower bound 1.0. The null effect (1.0) is always inside the slider. A1's percentages (15%, 7.5%, 7.7%) are about another venue. They must not appear as defaults or as targets. At most, docs/method.md cites them as context.

KPIs (all computed per rep, then aggregated across reps):

  • Walk-away % = (balked + reneged walk-ins) / walk-in arrivals. Booked parties are reported separately.
  • Lost parties = balked + reneged. Lost covers = their pax.
  • All-arrival wait: W_i = min(seat, renege, horizon_end) − arrival. Balkers have W = 0 and are flagged. A party is censored if it reneged or was still queued at horizon end. The mean over all arrivals is labelled "lower bound (censored)".
  • Median and p90 time-to-seat come from a Kaplan-Meier estimate with reneged and unfinished parties right-censored. If the survival curve never falls to 0.1, show p90 as "> X min (not estimable)" and never as a number.
  • Utilisation = occupied seat-minutes / (total seats × open minutes). Also report seat-fit = occupied seats / seats at occupied tables, because 2- and 4-tops waste seats on odd-sized parties.
  • CIs: N ≥ 200 reps. Report the t-interval of per-rep KPIs; use a bootstrap for p90.
  • Paired comparison with common random numbers: each process (arrival, size, booking, patience, balk-uniform, dwell, lounge, takeaway) gets its own mulberry32 stream seeded from hash(base_seed, rep, stream). All draws for a party happen at arrival in a fixed order, so changing the scenario never shifts the arrival stream. Report the mean of d_r = KPI_scn − KPI_base with its CI, plus the share of reps where d_r < 0.

Calibration (honest scope). For Khar, one walk-in row (party of 6-7, about 30 min, seated) gives one right-censored observation: that party's patience was at least 30 min. That is a consistency check, not a calibration. The UI should report "share of simulated 6-7 parties in the evening seated within 30 min" and set calibration status to "Insufficient evidence". The booked row (party of 18) gives an OBSERVED table-join time of 5-10 min (n = 1). The Chembur rows are a different outlet with unknown outcomes, so they are excluded by default. Build calibrate() as a censored-likelihood fit that only switches on above a stated minimum n, ready for the fieldwork listed in register section E.

Sensitivity. Run a one-at-a-time tornado over the slider range of each ASSUMED parameter, holding the others at default. Use the same CRN seeds and N = 200 per end. Plot the KPI delta with its CI and grey out bars whose CI crosses 0. Run it in the worker, after the main run. Global methods (LHS / Sobol) are deferred.

Risks if ignored:

  • Data integrity: a seated-only wait or an uncensored mean repeats Gemini's survivorship bias and makes waits look better than they are.
  • Reliability: unsynchronised RNG streams turn scenario deltas into noise. Without CRN, 200 reps may not separate A from Baseline.
  • Credibility: made-up rupee spend or effect sizes, once shown with CIs, look measured. One reviewer question sinks the project.

Dependencies:

  • Architect: approve range and gate as fields; worker message schema for rep_kpi.
  • Guardian/conductor: whether photo-derived table sizes (2/4 seats) may be cited as OBSERVED when the photos themselves are not published.
  • Advocate/Artisan: how to render null revenue and "not estimable" p90.
  • Skeptic: review the slider ranges set in Phase 2.

Core recommendation: Build the scene from a layout.json derived from the sketch rectangles. Every element in it carries an evidence tag and an open-question id, and the look comes from materials and light seen in the two photos, not from the brief's generic taproom list. Every invented fact is shown in the scene through one shared token system: an evidence overlay, hotspot cards and a persistent "layout partly assumed" badge. Key argument: The references give us a strong material and lighting story. They give us almost no geometry. The photos establish:

  • pale pine boxy furniture: bar-height 4-seat tables with stools on the awning side, standard 2- and 4-seat tables with white-cushioned chairs in the hall;
  • a wood-plank floor and white textured plaster walls;
  • a white tent-fabric pitched roof on steel tubes with a scalloped valance;
  • frameless glass walls with black corner mullions;
  • white dome pendants, ceiling fans, and globe lamps on a low white wall;

Because the image is built mostly from observed material cues, the look can be photographic while every dimension is honestly ASSUMED. That only works if the HUD and the scene use one token set for evidence.

  7. Hotspot cards. Each card shows:
  8. a title and an evidence chip;
  9. "What we know" (with the source file) and "What is assumed";
  10. "What would change this", plus the OQ-xx link to docs/open-questions.md.

Tuner Position — Phase 1 module structure under performance constraints

Core recommendation: Run the sim in two workers: a live worker for the animated run and a batch worker for the replications. Only small messages should cross the boundary: event deltas for the live view, and per-replication KPI rows (transferable typed arrays) for the batch. On the render side, the module structure needs four things from day one: a quality-tier table, a frame-time monitor, crowd instancing via baked vertex-animation textures, and a per-tier asset manifest. If these are bolted on later, the scene modules will have to be rewritten.

Key argument: Nothing has been measured yet, so this section is about structure, not numbers.

(1) Batches. The live run and the batch run go in separate workers. That way a 200 x 4 batch never stalls the live animation's event stream. Start with one batch worker, not a pool. Replications run in chunks ordered by replication index across all four scenarios: rep i uses seed s_i for A, B, C and D. This keeps the seeds paired, and partial CIs can be shown as the batch runs. After each chunk the worker posts {done, total} for the progress bar. When params change, a generation token cancels the stale batch. The cache key is hash(canonical params subset + scenario id + seed-set base + N + engine version). Results live in an in-memory Map. Optionally, the default-params baseline can be precomputed at build time by running the same TS engine under Node, and shipped as JSON tagged SIMULATED with its seed set. Then the first view shows CIs with no wait. Add a pool (size min(hardwareConcurrency - 2, 3), at least 1) only if measured batch time misses its target.

The tornado chart (6 drivers x low/high x N runs) is a separate, lower-priority job that runs on demand behind the main batch. It never runs automatically on every slider move.

(2) The boundary.

  • Live worker to main thread: discrete event deltas (arrive, queue, seat, renege, depart), packed into an Int32Array/Float32Array. They are batched at a capped rate (target 10 Hz) and sent as transferable buffers. Agent count is in the low hundreds, so bytes are trivial. The real cost is message frequency and GC. A KPI snapshot for the HUD goes out at a lower rate (target 2 Hz). The renderer owns path interpolation; the sim never sends per-frame positions.
  • Batch worker to main thread: per-replication KPI columns (one Float64Array per KPI) plus computed aggregates. Full event logs never cross, except for one selected replication on demand (for export/audit).
  • No SharedArrayBuffer. GitHub Pages cannot set COOP/COEP headers.

(3) Scene. On phones, the expensive items in the graphics brief are, in order of expected cost (unmeasured):

  1. N8AO/SSAO: a full-screen, depth-bound pass.
  2. Dynamic soft shadows from more than one light, plus the characters in the shadow pass.
  3. Volumetric light shafts and DOF.
  4. Individually skinned characters: one draw call each, doubled by shadows. This alone can break the 300-call cap.
  5. Device pixel ratio above 1.
  6. Selective bloom, which needs a layer or extra pass.

Mitigations:

  • People: InstancedMesh with baked vertex-animation textures, giving one draw call per model variant per LOD.
  • String lights: instanced emissive meshes, not point lights.
  • Shadows: one shadow-casting key light. Furniture shadows render once (autoUpdate=false). People get blob shadows on Medium and Low.
  • Post chain: SMAA, bloom, vignette and LUT merged into a single EffectPass. AO runs half-res on Medium and is off on Low.
  • Assets: KTX2 textures (ETC1S for albedo, UASTC for normals), plus meshopt/gltfpack geometry. Low gets its own texture set, so it never downloads High maps.
  • Loading: shaders are precompiled behind the loading screen.
  • Auto-downgrade: triggers on the rolling median frame time over about 120 frames, if above 22 ms. It ignores the first seconds after load. Hysteresis applies, and it never auto-upgrades.

(4) docs/performance.md. Every budget figure is labelled TARGET. Each row has the columns Target | Measured | Device | Browser | Build hash | Date | Method. Measured cells read "Not measured" until someone measures them.

What to measure, on a fixed benchmark camera path per tier:

  • frame time p50/p95
  • draw calls and triangles (renderer.info)
  • texture count and estimated GPU texture memory
  • JS heap
  • gzip size per chunk and first-load bytes
  • time to interactive
  • batch wall time for 200 x 4 on each device
  • live message rate

Measured values are tagged OBSERVED and name the device.

Module implications: src/sim/ stays pure (no DOM; runs in Node for tests and precompute). Alongside it: src/sim/protocol.ts (versioned message types), worker-live.ts, worker-batch.ts and cache.ts. Render side:

  • src/render/quality-tiers.json, which holds render config, not venue facts, so it stays out of params.json
  • src/render/frame-monitor.ts
  • src/render/crowd/
  • src/render/post/
  • src/assets/manifest.ts, with per-tier variants and byte sizes for the progress bar
  • a ?perf=1 overlay

  • Skinned characters, one per mesh, plus multi-light shadows go past 300 draw calls and miss 30 fps on phones. Fixing this later means rewriting the people module.
  • A single worker that does both live and batch runs freezes the animation during the batch. Recomputing the tornado on every slider move makes the sliders unusable.
  • Phones download High-tier textures and the HDRI, which wastes data and memory and risks the tab being killed.
